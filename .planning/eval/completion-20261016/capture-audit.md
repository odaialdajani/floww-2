## Root causes: proven versus not proven

**Proven coverage mechanism:** disabled scheduled capture plus opportunistic fresh builds does not establish a continuous observation stream. Strict known-at, 15-minute age and immutable scope matching correctly reject the stored rows outside their actual ownership. The preserved default scope's zero matches cannot be fixed honestly by borrowing another scope's nodes, extending freshness arbitrarily, or using today's chain.

**Proven durability hazard:** an unset path at import, or a file-engine initialization exception, creates a memory singleton; subsequent path configuration does not repair that object. Earlier actual memory backing was measured. However, **the precise earlier startup event is unresolved**: no matching `DUCKDB_PATH`/memory-fallback/lock/OOM/resource-exhaustion line was found in the targeted 16-October review and history-diagnosis logs. Both `.env` import order and a real bootstrap regression test already exist. The earlier memory state alone cannot establish whether its cause was missing import-time configuration, a lock/open failure, an older loaded module or resource exhaustion.

**Proven engineering resource gaps, not a demonstrated OOM:** the engine constructor does not explicitly set DuckDB `threads`, `memory_limit` or a spill path (`duckdb_engine.py:126–144`). Snapshot writes launch a task per fresh build; the shared connection lock serializes correctness but does not bound the number/bytes of pending task payloads. Each record also rechecks DDL/additive migrations (`heatmap_history.py:194–232,381–382`) and inserts contract rows individually (`:492–518`). No snapshot archival policy is established by the cited producer/store path. These are concrete load/backpressure risks; they do not prove why any historical worker failed.

Read-only `lsof` measured the current DB file at 1,762,930,688 bytes and WAL at 11,135,057 bytes. `ps` later measured PID39759 RSS at 751,616 KiB, CPU 24.4%, process start `Fri Oct 16 16:06:29 2026`. Those are separate instantaneous disk/process observations, **not** a leak, OOM diagnosis, retention budget or restart proof. No settings or secrets were read.

**Write-ack gap:** fresh-build success is not durable-write success. The scheduled loop awaits `_build_heatmap_impl`, which schedules the storage thread rather than awaiting its COMMIT result. A later `record_snapshot=None` is not incorporated into that loop's success accounting. Explicit record-now (`routes/price_history.py:99–143`) waits for replay visibility up to 20 seconds, but ordinary fresh builds do not. A shared bounded writer receipt would improve this without activating a worker.
