Review — agentic layer for Solstice + Tidehunter Pro

Verification pass on the approved plan · 2026-09-05 · working tree 4d9715b, clean

The shape is right and worth building. Four things in it would have failed on day one: the main endpoint can't be reached from the browser, the data layer can't be called the way the plan assumes, the number-checking gate would have been switched off within a week, and the assistant could starve the trading desk of its own data budget.

No redesign needed — nine blocking corrections, nine gaps, three claims I overstated, and three live bugs that exist whether or not this gets built. Two of those bugs mean the "track record" machinery I said to reuse is not built; it is built wrong.

Blocking corrections — fix in the plan before stage A

P0

"Call service functions directly" is true for 7 endpoints, partly true for 7, and false for 5

The plan treats every data source as a clean importable function. Reality splits three ways, and the split has to be declared per tool rather than assumed.

Genuinely direct: /air-pockets, /beach-ball, /reverse-rug, /rainbow-road, /live, /drilldown, and the three snapshot reads. Plus /api/heatmap/{ticker} via server.build_heatmap.

Callable, but the chain has to be fetched and gamma-enriched first: /flip-zones, /node-lifecycle, /velocity-mode, /stacked-nodes, /tug-of-war, /alerts/feed, /alerts/quality.

Logic lives in the route handler, not a service: /scan, /regime/{t}, /trinity-confluence, /node-classification, /rolling-floors-ceilings. There is no importable equivalent to call.

/scan is the hard one. It owns an hourly spend budget against a metered third-party feed, with single-flight locking, 429 backoff and two fire-and-forget writes that keep the alerts table alive. Re-implementing that burns the cap.

Fix

The registry declares a call style per tool: direct (import the service function), enriched (fetch via the route module's cached chain helper first), or internal-http (loopback call — reserved for /scan, which must not be duplicated). Three styles, stated up front, instead of one assumption that breaks on a third of the surface.

services/flowseeker.py is 436 lines and exposes 4 functions. routes/flowseeker.py is 1,879 lines and carries 22 module-level helpers, a rate-limit budget state machine and the whole alert pipeline. That asymmetry is the finding.
P0

The failure mode is an empty answer with a 200, not an error

Two things compound. The shared chain fetch can return contracts with no gamma on its deepest fallback path, and every gamma-based aggregator skips contracts where gamma is zero or missing. So a tool that fetches the chain the obvious way and then asks for flip zones gets {"flip_zones": [], "count": 0} — no exception, no error field. On top of that, every one of these handlers catches its own exceptions and returns HTTP 200 with status: "degraded".

An agent reading that will confidently tell you there are no flip zones. The truth is that it never had the data.

Fix
  • Enriched-style tools fetch through the route module's chain helper, which applies the gamma backfill and a 30-second cache. Never through the raw merged fetch.
  • The evidence ledger records, per tool: which upstream actually served the data, the degraded flag, and the contract count.
  • Hard rule in the prompt and in code: an empty result is never narrated as a finding. It is reported as missing data, with the source named.

P0

Latency is worse than the plan implied, and the caches are easy to miss

The chain fetch is a three-tier cascade with a 30-second timeout on each of the first two tiers before the third even starts. Worst case for one cold ticker is around a minute. There are four independent caches in front of this, none of them in the service layer, with no shared invalidation — so calling the "obvious" underlying function bypasses most of them.

There is also an exact-argument trap. The flow regime endpoint deliberately calls the heatmap builder with the same argument tuple the front end uses, so it lands on the same cache key. A tool that calls it with different arguments silently doubles the upstream load instead of sharing the cache.

Fix
  • Prefetch goes through the cached entry points only, with the front end's exact argument tuple.
  • Every tool carries a deadline well under the cascade's worst case, and serves stale-from-cache rather than blocking the answer.
  • Keep the Alpha Vantage tools out of the parallel bundle entirely — that provider is rate-limited to five calls a minute.
P0

The screen context cannot come from where the plan puts it

The plan mounts the panel in the app shell and has it read what you are looking at. The shell only receives the page name, the navigation callback, and two user fields. Ticker, timeframe, metric, expiry count and selection all live one level up, in the frozen file.

Fix — and it needs zero edits to the frozen file

Put the conversation state in a provider at the shell, and mount a small reporter inside each of the two tab components. Both of those already receive everything needed — the Solstice grid is handed ticker, spot, data, timeframe and the DTE selection as props today, and the Tidehunter tab owns its own state. Neither file is frozen.

Also: the shell's outer container has no positioning context, so the panel must be fixed-position rather than absolute.

P0

The core data functions live in the server module, not the service layer

Both the heatmap builder and the shared chain fetch are defined in the main server file. A service-layer registry that imports them at module load will deadlock the import graph.

Fix

Import them lazily, inside the tool function, at call time. This is already the house pattern — an existing service does exactly this today, and dozens of route modules do it. Consequence worth stating: the registry has to run in the same process as the API. It cannot be a standalone worker.

This is not a hack. The accepted coupling ADR names the heatmap builder as part of the analytics layer by design.

Claims in the plan that were wrong

correction

The frontend package file is frozen — no new libraries at all

The plan assumed it could avoid adding a markdown renderer. The real constraint is stronger: nothing can be added. That turns out to be fine, and better than expected.

Already installed and currently unused by a single line of code: a command-palette library, a drawer/sheet library, and a toast library — precisely the three the panel and pop-up bar need. The data-fetching library is installed and its provider is already mounted at the app root. Twenty-eight accessible UI primitives are there too.

Two real consequences: there is no markdown renderer and no HTML sanitiser available, so the answer must render as structured sections rather than model-authored markup — which the plan already wanted for other reasons. And the front end is on React 19, not 18 as the project doc says.

correction

The "leaked API key" is a truncated prefix, not a usable key

The tracked audit report lists value prefixes only; every entry is cut off. No full key string is in version control. The audit still graded it critical and the underlying key in the untracked environment file is presumably the same one, so rotating is still right — but this is a housekeeping item, not a blocker on this work.

correction

"Every read request is unauthenticated" — true by default, not universally

Reads skip the key check by default, but a route can opt in to requiring it, and three broker routes already do. One admin surface is gated for all methods. The plan's endpoint shape still works exactly as designed: the ask is a write and needs the key, the stream is a read and does not. One detail to handle — when the server key is unset, writes fail with the same status code the language-model layer uses for "no provider configured", so the two are indistinguishable to the caller. Use a distinct error body.

Constraints the plan missed

new

An accepted architecture decision governs where this can sit

There is a binding one-directional rule: the policy and execution layer may read the analytics layer, never the reverse. The agent is a third consumer sitting above both. It must be written so it never becomes a back-channel that lets analytics see execution state. Worth recording as the next numbered decision record — the read-only tool boundary is exactly the kind of thing that file exists for.

new

A scheduler already exists — and the one that looks obvious is dead

There is a live in-process daily scheduler in the server that already fires a warm-up pass and refreshes policy on a timer. The separate cron configuration file looks like the right place but writes to a system crontab that does not exist on this machine, is never called by the server, and has stub jobs. The background watcher and daily brief hook the live loop, not that file.

new

Ticker coverage is far narrower than the inspiration implies

The screenshot that started this does full end-to-end research on a single small-cap name. This platform's spine is built for a handful of index products: machine-learning models exist on disk for exactly five tickers, the live tape gates to six, and the flow watchlist is ten names. Structure and flow will work for arbitrary tickers through the chain, but the model leg and the paid tape simply will not be there.

Fix: each tool declares its coverage, and the answer states which legs are missing rather than quietly producing a thinner read. Otherwise the agent looks confident and is actually half-blind on anything outside the core names.

new

Three smaller things that will bite on day one

  • Every tool result must pass through the existing sanitiser before it reaches the model. It converts not-a-number and infinity to null and numpy types to native ones. Skip it and either the payload fails to serialise or the string "NaN" lands in the context and gets read as a value.
  • The historical snapshot store is capped at fifty records per ticker, which is the real ceiling on how far back the "cumulative" read can look.
  • The stream framing convention is hand-rolled and exact — copy it verbatim from the existing flow stream rather than reaching for a library, since none can be added anyway.

Live bug found — unrelated to this build

bug

Three shipped panels return empty results on the fallback data path

Rolling floors and ceilings, stacked nodes, and tug-of-war each fetch the chain directly instead of through the helper that backfills gamma. Their maths then discards every contract. On the primary data source gamma is present and they work; when the feed falls through to the last-resort provider, they go quiet — empty arrays, status 200, no error. In other words they fail exactly when everything else is already degraded, and nothing in the UI says so.

Rolling floors and ceilings has a second, unconditional defect. It needs a series of daily snapshots to detect a trend; the handler builds a list containing one live snapshot. A one-element series has no trend, so the reading is always flat and the signal always neutral, and the lookback parameter it accepts does nothing at all.

Fix

Point all three at the enriching helper — a one-line change each, and it also gets them the shared cache they currently bypass. Rolling floors and ceilings needs the real snapshot history wired in, which already exists in two stores.

bug

Your published alert hit-rate is measuring the wrong thing

Every scan rewrites the recorded move on every open alert for that underlying to "price at alert versus price right now", with no age filter and no horizon. The same bullish alert scores as a win at eleven and a loss at three-thirty. Whatever the last scan saw is what the quality panel reports. The pass/fail threshold is a flat half a percent for every ticker and every timeframe.

This matters beyond the agent: the tier locks and the conviction calibration you already look at are built on this number.

bug

The analytics database is in memory — its history dies on every restart

The engine is created with no file path, so it defaults to memory-only. Alert history, tier locks and the calibration curve are all wiped whenever the backend restarts. Anything that wants a track record has to go in the durable store instead.

What held up under checking

verified

Fourteen claims confirmed against the code

  • The broker order path is genuinely ungated and points at a live gateway. The plan's read-only-by-construction requirement is necessary, not defensive. The separate gated path has thirteen tests holding it closed — reproduced.
  • The language-model service is synchronous and awaited from async routes. It will block the whole server. Fixing it in stage A is correct.
  • Six libraries are imported by live code and missing from the requirements file, including the one behind an entire agent surface — which is why that surface silently returns not-found today. The plan is right not to build on it.

  • Backend collection reproduced at 4,650 tests, zero errors — the project docs say 4,640, which is normal drift.

Second pass — design holes (all verified against the tree)

P0

The main endpoint cannot be called from the browser at all

The plan makes the "ask" a write so it can carry a body, and the stream a read so it needs no key. But the front end has never sent an API key anywhere — searching the entire source for it returns nothing. So the flagship endpoint answers "unauthorised" from the first click, or "unavailable" if the server key is unset.

Second half of the same problem: reads are exempt from the sixty-per-minute limit only for a fixed list of path prefixes. The agent's path is not on it, so stream reconnects get throttled.

Fix

Add the agent path to the public list with an explicit comment saying why, and to the rate-limit exemption list. Decide this now — it is two lines and it is the difference between working and not.

P0

The assistant can starve the desk of its own data

The flow desk rations its upstream vendor to twenty calls an hour, of which fourteen are reserved for the scanner and one is held back — leaving five chain calls an hour for everything else, globally. The shared chain fetch used by the heatmap does not consult that budget at all; it is separate accounting. So the agent's prefetch, watcher and daily brief would spend the same vendor quota invisibly. When the vendor pushes back, the client pauses itself for ten minutes app-wide and all of Solstice drops to the weakest data source.

Fix — architectural, not a tuning knob

The assistant reads the desk's warm cache and never initiates an upstream fetch. If data is cold it says so, with a staleness stamp, instead of going and getting it. Give it a hard small slice of the hourly budget from one shared ledger.

P0

The track-record wheel is not already built — it is built wrong

My plan said to model the feedback loop on the two existing outcome systems. Both are broken, and copying either would produce a calibration curve made of noise.

The alerts one rewrites every open alert's move to "price at alert versus right now" on every single scan, with no age or horizon filter and a flat half-percent threshold for every ticker. A bullish call is a win at eleven and a loss at three-thirty; the published hit rate is whatever the last scan happened to see.

The model-outcome one is worse: it compares a five-day average daily return against a one-day prediction, with the comment "approximate" left in the code.

And the store underneath is in-memory by default — the analytics database is created with no file path, so the existing hit rates, tier locks and calibration all evaporate on every restart. That is a live problem today, not just for this build.

Fix

Design resolution once, properly, and put it in the durable store rather than the volatile one. A claim like "bearish into the 86 zone" is a race between two price levels, not a return threshold — grade direction, level-touched-before-invalidation, and invalidation separately, with buckets for "neither" and "couldn't resolve". Anchor to the horizon and never rewrite a resolved row. Stamp the resolver version, or retuning later makes the whole history uncomparable — which is exactly how the existing one broke.

Scheduling constraint that has to be designed in: minute bars from the primary provider only go back one day, so a same-session claim must resolve the same session or the path data is gone.

P0

The number-checking gate as I specified it will be switched off within a week

"Extract every number and match it against the evidence" false-flags constantly: money formatted to one decimal, billions written short, ratios the model computes itself from two stored values, time deltas, dates, and accidental collisions where a percentage matches a strike price. On a seven-section answer with around twenty-five numerals, expect eight to fifteen flags. It gets ignored, and then the stricter version makes the product unusable.

Fix — make the model cite instead of type

Every stored value gets an id. The model writes a reference, and the server substitutes the formatted number at render time. A bare numeral in a factual slot is then a flat protocol violation rather than a fuzzy match with a tolerance to tune. Derived quantities get a small server-evaluated form for ratios and time-deltas — which is exactly what the "cumulatively" ask needs, and it moves the arithmetic off the model. Keep a numeric scan only as a lint on what is left over.

Two free wins: hover-to-source in the panel, and the test harness compares ids instead of prose.

P1

Confidently wrong input is more dangerous than failure

When the database is unavailable, the node-history fetch returns an empty list, and the maths downstream treats that as "every node is fresh" — the docstring says so in as many words. So the assistant would report a pristine, untested structure when the truth is that nothing could be read. The proposed evidence record has no field that can express this.

Related, and it is the whole value proposition: when the chain comes from the weakest provider, gamma is back-computed from a textbook formula rather than supplied. The resulting surface is model-derived, not dealer-derived. The answer has to say which one it is.

Fix

Each evidence entry carries a status, a source and a staleness. Failed entries are barred from the answer; stale ones must be narrated as stale.

P1

The horizon is a day-one schema decision, not a later feature

No engine endpoint accepts a time horizon. They all take a count of nearest expiries. So "zero-day" today means "the one nearest expiry", which on a Thursday is Friday's chain — one day, not zero. Making the horizon real means slicing by expiry in the tool layer, which is fine, but it has to be in every tool signature and every cache key from the first commit. Add it later and every signature changes, the cache key changes, and every recorded test fixture is invalidated.

P1

Four conviction scores already exist, two of them only in the browser

There is a three-way index confluence score, a row conviction score in the flow tab, a scan score beside it, and a fourth weighted conviction on the server. My plan said to rebuild the browser one in Python — which means two copies of the same number, drifting. There is already a comment in this codebase telling a future reader to keep a constant identical across the two languages, so the tax is known.

Fix: use the server-side one, which is already Python, already stored and already calibrated. Do not create a fifth. Weights live in one versioned config stamped into every record, so changing them is a gradeable event. And the model must be allowed to disagree with the score in a separate line — a narrator that can only agree produces reasoning you cannot grade, which defeats the point.

P1

Cost: two of the proposed tools can blow a whole turn on their own

Most tools return small summaries and fifteen of them is a manageable input. But the raw chain and the full grid are enormous — a full chain is over thirteen thousand contracts, and the grid is thousands of cells. One careless tool call dwarfs everything else.

Realistic per-question cost on a strong model is ten to twenty-five cents. Thirty questions a day plus a ten-name morning brief plus a watcher firing the full research bundle on every high-conviction alert lands somewhere between five and twenty-five dollars a day, for one user. As written the watcher is an unbounded spend loop attached to an alert feed.

Missing controls: a hard daily budget that degrades to the cheap model and then to the existing deterministic template; prompt caching on the stable instruction prefix, which is the single biggest cost lever and I never mentioned it; watcher coalescing to one bundle per ticker per quarter-hour; and per-tool output caps that mark truncation explicitly rather than silently. Raw chain should be an internal fetch, not an offered tool.

Also: escalating to the strong model "on estimated tool count" is unimplementable — you cannot count the tools before running them. Escalate on question class instead.

P1

Read-only by construction needs to be structural, not a list

My proposed test only checks the function each tool registers directly. A tool that reaches an order path three calls deep passes it. Given that one order path is ungated and points at a live gateway, make it structural: a test that loads the agent package in a fresh interpreter and asserts the order modules were never imported at all; a lint rule forbidding those imports from the agent package, which rides the existing lint gate for free; and a source scan for order-shaped method names. About a day's work.

P2

Conversation memory was never designed, and it decides the backend shape

The plan has three endpoints keyed on a turn and never says where a turn lives. Unanswered and blocking: where turns are stored and whether replay survives a restart; whether a follow-up question re-runs the whole data gather; what happens when two questions run at once on the same ticker; how a turn expires; and what happens when someone refreshes the page mid-answer, which currently would double the spend with no way to cancel. Every existing stream in this codebase caps its duration; this one has no cap and no cancel.

P2

The cheap-model tier has no job in version one, and its libraries are not installed

Neither of the two non-primary model libraries is in the dependency list, so that path fails on import before it even reaches its outdated model name. And the jobs the cheap tier was meant to do are the morning brief — which an existing deterministic generator already produces — and a one-line answer. Cut the router from the first stage, hardcode one model, and add routing when a month of real cost data shows where the money goes.

Revised read on effort

Roughly thirty to forty-five days of build as written. The rescoping below brings the first two stages to about twelve to seventeen, which is the honest version one.

Move into stage one: the horizon in every tool signature and cache key; status, source and staleness on every evidence entry; the cite-don't-type protocol, because it shapes both the instructions and the test harness; the shared upstream budget accounting; and writing claim rows — not resolving them. Claims are cheap to emit and impossible to backfill, so if stage two doesn't write them, the track record has no history to point at later.

Move out of stage one: the model router, and about twenty-eight of the thirty-eight tools. Ship the eight to ten the standard bundle actually uses. Every extra tool costs instruction tokens and a recorded test fixture. Note two of the proposed tools aren't functions yet — the alert feed and quality logic sit inside the web handler and need extracting first.

Collapse stage three. With the horizon moved up, what remains is the time-delta read — and that is the single highest-value piece for the "cumulatively" ask. A static-frame read is what the panels already show; the agent adds nothing there. Pull it into stage two.

What gets abandoned half-built, bluntly: the track-record stage almost certainly — longest, least visible, payoff two months out, and at a handful of verdicts a day the three-hundred-claim gate is sixty trading days. The background watcher probably: it will produce noise before value and get muted inside a fortnight. And the confluence weights will ship as somebody's guess and never be revisited unless the disagreement line forces the question.

Stages one and two are the honest version one. That was buried at the bottom of the plan as a risk; it belongs in the build order.

Minor: the plan's verification section calls the bare interpreter a "3.11 syntax oracle". It catches syntax, not standard-library drift — which is the actual risk of developing on one version and shipping on another. Run the suite under the shipping version in the pipeline instead; the image already exists.
